# 検証機能の分離案

作成日：2026年9月16日。**バージョン0.2.0で実装した分離方針です。** 利用者向けの最新手順はプラグイン同梱の `help/validation-en.md` と `help/validation-ja.md` を参照してください。

## 方針

GeoParquet・PMTilesの作成は維持します。容量を占めるrashidとその依存ライブラリを
公式配布ZIPから除外し、詳細検証は利用者または公開担当者が別環境で実施します。
カタログ作成は引き続きQGISのGUIだけで完結します。外部での詳細検証は別の作業です。
プラグインから外部ライブラリを自動ダウンロードしたり、データをクラウドへ送信したりしません。

## プラグイン内に残すチェック

既存のQGIS環境のGDAL/OGR、PyArrowとPython標準ライブラリを利用します。
これらをプラグインに追加同梱する方式にはしません。

| 項目 | 方針 |
| --- | --- |
| 入力値、ID、CRS、形状型、公開列の確認 | 既存処理を維持 |
| 入力スナップショットとGeoParquetの件数比較 | 維持 |
| 公開属性・形状のハッシュによる照合 | 維持 |
| GeoParquetの読み取りと属性統計 | 維持 |
| PMTilesのヘッダーと再読み込み | PMTiles出力時のみ維持 |
| 生成JSONの読み取り、必須ファイルとローカル参照先の存在確認 | 基本チェックとして明示的に実装 |
| rashidによるPortolan/STAC・実データの詳細検証 | 外部作業へ移す |
| 公開先のHTTP Range・CORSの検査 | 公開後の外部作業として案内 |

残すチェックにも実データの読み取りは含まれます。「実データを一切検査しない」という変更ではありません。
ただし、基本チェックをPortolan仕様への完全適合判定として扱わないことが必要です。

## 作成結果と表示

基本チェックの失敗は従来どおり出力確定を止めます。
外部詳細検証が未実施という理由だけでは、出力確定を止めません。
「作成完了」「基本チェック結果」「詳細検証状態」「公開先検証状態」を分けて記録します。

成功時の日本語表示案：

> カタログとデータを作成しました。作成時の基本チェックは完了しています。
> Portolan仕様への適合性と実データの詳細検証は未実施です。
> 公開・配布前に「詳細検証の手順」を確認し、別環境で検証してください。

英語表示案：

> Catalog and data created. Basic export checks completed.
> Detailed validation of Portolan conformance and asset data has not been run.
> Before publishing or distributing, follow the Detailed validation guide in a separate environment.

結果画面に「詳細検証の手順」「出力フォルダーを開く」「作成レポートを開く」を設けます。
英語を標準とし、QGISの言語が日本語の場合は日本語に切り替えます。
「検証済み」「完全適合」「詳細検証成功」とは表示しません。

作成レポートの状態例：

```json
{
  "build_status": "completed",
  "basic_checks": {"status": "passed"},
  "detailed_validation": {"status": "not_run", "reason": "external_validation_required"},
  "hosting_validation": {"status": "not_run"}
}
```

`passed: true` 一つで作成と詳細検証の成功を兼ねる構成を廃止します。
現在の `local_validation_complete` の扱い、結果画面、テストも合わせて変更します。
外部レポートの自動取り込みは初期対応に含めず、プラグイン上で未検証を勝手に成功へ変更しません。

## 利用者に提示する詳細検証の手順案

以下は、現行実装が使用しているrashid 0.1.8を基準とする手順案です。
CLIオプションは同梱済み0.1.8のソースと公式READMEで確認しました。
別環境への新規インストールを含む一連の動作試験は、分離版の実装時に実施します。

### 1. 検証用環境を準備する

QGISのPython環境にインストールせず、別のPython環境を用意します。
例えばuvが利用できる環境では、次のコマンドで検証ツールを独立した環境へ導入できます。
uv自体の導入は[公式手順](https://docs.astral.sh/uv/getting-started/installation/)に従います。

```text
uv tool install "rashid==0.1.8"
```

初回のツール取得にはインターネット接続が必要です。対応PythonとOS用の依存パッケージが必要です。
ツールがPATHに見つからない場合はuvの案内に従って設定し、ターミナルを開き直します。
バージョン固定だけでは依存パッケージ全体の再現性は保証されないため、公開担当者は実際の環境も記録します。

### 2. 出力カタログ全体を検証する

`OUTPUT_FOLDER` を、プラグインが作成した `catalog.json` のあるフォルダーに置き換えます。
個々のParquetファイルだけでなく、生成されたカタログのフォルダー構造全体を保持してください。

```text
rashid check "OUTPUT_FOLDER" --schema --data-scope local
```

機械可読レポートを保存する場合は、次のように実行します。
レポートの保存先はカタログの外にします。

```text
rashid check "OUTPUT_FOLDER" --schema --data-scope local --json > validation-report.json
```

### 3. 結果を確認する

- エラーがあれば対象ファイルとルールIDを確認し、設定や入力データを修正して再作成します。
- 警告は内容を確認します。検証不能・検証スキップを、検証成功として扱わないでください。
- PMTilesを意図的に出力していない場合の推奨事項の警告は、仕様と用途を確認して判断します。
- 終了コード0だけで全検査が完了したとは判断せず、警告と実行された検査範囲も確認します。
- 検証後にデータやJSONを変更した場合は、再検証します。
- QGISの属性表・地図と、生成したPMTilesの表示も確認します。PMTilesの簡略化やタイル分割により、
  表示上の地物数は元データの件数と一致しない場合があります。

### 4. 公開後に配信設定を確認する

公開URLを設定して、Range・CORS等の配信条件を検査します。
以下のURLは例であり、実際に公開したカタログのベースURLへ置き換えます。

```text
rashid check "OUTPUT_FOLDER" --schema --data-scope local --live --live-base-url "https://data.example.org/my-catalog/"
```

この手順では公開先への通信が発生します。ローカル検証だけでは公開先の設定は確認できません。

## 説明書の配置

検証ガイドを英語・日本語の両方でプラグインに同梱し、結果画面からオフラインで開けるようにします。
生成するREADMEにも「基本チェック完了・詳細検証未実施」を記載し、検証手順を添付します。
カタログへ添付する文書は文書用アセットとして登録します。
作成レポートは引き続きカタログの外側の `.build-report` に保存します。

## 実装時の変更範囲と確認項目

- `engine.py`：rashid・ワーカー必須条件を外し、出力確定条件を基本チェックへ変更。
- `ui.py`：作成結果と検証結果を分けて表示し、ガイドへのボタンを追加。
- `catalog.py`：生成文書の検証状態と検証手順を更新。
- `scripts/package.py`：公式配布版から `_vendor` を明示的に除外。元フォルダーに残っていても同梱しない。
- プロファイル、メタデータ、翻訳、README、公開準備状況、ライセンス説明を新構成に更新。
- rashidをプラグインの必須実行依存から外す一方、開発者の別環境で成果物の詳細検証を継続。
- `_vendor` のない環境で作成が成功すること、基本チェック失敗時は停止することを試験。
- GeoParquet作成・PMTiles有無・英日表示・検証状態の記録を回帰試験。
- 配布ZIPの容量、ネイティブバイナリ非同梱、新規インストール動作を再確認。

この変更で利用者側に追加の検証ライブラリを要求しなくなりますが、変換用のGDALドライバーと
PyArrowがQGIS環境に必要である点は残ります。OSを問わず動くことや公式承認を保証する変更ではありません。
